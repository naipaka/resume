#### 推し活マッチングアプリ開発

| 項目       | 内容                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| 期間       | 2023/04〜現在                                                            |
| チーム規模 | アプリ開発 3〜4 名、サーバーサイド開発チーム                             |
| 役割       | アプリ設計、API 設計、実装、テスト、チームマネジメント                   |
| 使用技術   | Flutter、Dart、Firebase、StoreKit 2、Pigeon、GitHub Actions、Xcode Cloud |

既存アプリの機能開発と運用を、2023 年から継続して担当しています。
アプリ開発チームは 3〜4 名で、API はサーバーサイドの別チームが実装しています。

仕様とデザインは顧客から提供されるため、どのような API が必要かは、画面を実装するアプリ側で最初に見えてきます。
一方で、API が先に作られると、アプリに必要なデータが含まれず、チーム間のやり取りに手間がかかっていました。
そこで、アプリ側で API 仕様の草案を作ってから実装を始める進め方へ切り替え、最初の草案を作成しました。
その後も、この進め方で開発を続けています。
また、仕様が決まっていない機能や影響の大きい移行では、選択肢を比較して提示し、合意を得てから進めています。
例えば、メンション機能ではデータの持ち方を比較して設計し、アプリ内課金の StoreKit 2 移行ではサーバー側の検証方式を 2 案で提示しました。
StoreKit 2 への移行後も、課金に関する障害や問い合わせは発生していません。

原因がすぐにわからない不具合の調査も、継続して担当しています。
これまでに、クラッシュレポートを影響するユーザーの多いものから整理して修正したり、アプリの容量が膨らみ続ける問題をライブラリの不具合まで遡って解消したりしました。
中でも、プッシュ通知を受け取ったときのアプリ側の処理が特定の条件で実行されない不具合では、エラーが記録されず、チーム内でも再現できないまま調査が止まっていました。
そこで、アプリの状態と起動方法の組み合わせを検証して再現条件を特定し、OS ごとに異なる原因を突き止めて解消しました。

さらに、リリース作業の自動化にも取り組みました。
以前は各開発者が手元の環境でリリースビルドを作っていたため、Xcode のバージョン違いでビルドに失敗したり、リリースする変更が含まれていなかったりする問題がありました。
そこで、GitHub Actions と Xcode Cloud でビルドからストア提出の直前までを自動化し、誰が実行しても同じ環境と手順でリリースできるようにしました。
その結果、人が操作する時間は 1 回のリリースにつき約 1〜2 分になりました。
Xcode Cloud は無料枠で運用しており、構築した仕組みはほかのプロジェクトにも展開しています。

参考：[Xcode Cloud を使った TestFlight デプロイの構築記録](https://zenn.dev/naipaka/scraps/807963171ec6d9)

#### カーシェアアプリ開発

| 項目       | 内容                  |
| ---------- | --------------------- |
| 期間       | 2025/11〜2025/12      |
| チーム規模 | アプリ開発 2 名       |
| 役割       | メイン実装            |
| 使用技術   | Flutter、Dart、Stripe |

既存の iOS アプリ（Swift）を基に、Flutter で Android アプリを開発しました。将来的な iOS の Flutter 移行も見据えて両プラットフォームへ対応できるよう設計し、機能単位で役割を分担しながら、コードの共通化を進めました。

メイン実装として `flutter_stripe` を導入し、予約から決済までの一連のフローを構築しました。
API エラーハンドリングは共通処理にまとめ、各画面から同じ方法で扱えるようにしました。

決済機能の実装中、Android の CustomerSheet でカードブランド画像を表示できない問題が発生しました。
パッケージの Kotlin 実装まで調査し、画像の読み込み方法と Base64 エンコードに原因があることを特定しました。
案件側ではカードブランドに応じた画像へ切り替える処理で暫定対応し、恒久対応に必要な再現手順、原因、修正案を [Issue #2280](https://github.com/flutter-stripe/flutter_stripe/issues/2280) と修正ブランチで開発元へ共有しました。

`initCustomerSheet` は、値を返し得る型で定義されている一方、実際には成功時も `null` が返るため、戻り値を前提とした処理を組めない問題もありました。
iOS・Android の実装と React Native SDK を比較して実際の動作を確認し、案件側のロジックを修正しました。
併せて [Issue #2283](https://github.com/flutter-stripe/flutter_stripe/issues/2283) を作成し、実際の動作に合わせて戻り値型を修正する [PR #2284](https://github.com/flutter-stripe/flutter_stripe/pull/2284) を提案しました。

サーバーから配信する文言の多言語対応が論点になった際は、カップル向けアプリで行った検証と技術比較を記事で共有し、実装方式を検討する材料としました。
記事には、変数展開、複数形、型安全性、オフライン対応、翻訳データのバージョン管理まで含めた検討内容を整理しています。

参考：[iOS / Android アプリの多言語対応をサーバー側で管理する方法を検討してみた](https://zenn.dev/naipaka/articles/mobile-app-i18n-server-management-consideration)

### 会社・チームへの取り組み

#### コード品質とレビュープロセスの改善

PR レビューでは、規約の確認や設計のすり合わせがテキスト上に集中し、1 つの PR でコメントのやり取りが 40〜60 件に及ぶことがありました。
そこで、機械的に判定できる規約は、社内の lint パッケージに Custom Lint のルールを 9 件追加し、エディタと CI で検出できるようにしました。
導入後、対象にした規約についての指摘はレビューで出ていません。
一方、設計や実装の判断が必要な箇所は、画面共有で話しながら確認する方法に切り替えました。
その結果、やり取りは 10 件以下まで減り、PR のマージが早まったことで、再レビューで使っていた時間を機能実装へ回せるようになりました。
なお、追加した lint ルールは社内のほかのプロジェクトでも使われ、社外のリポジトリからも利用されています。

#### 組織とチームの働き方への提案

会社として目指す方向が明文化されておらず、1on1 で話す目標も個人ごとに閉じていました。
そこで、チームで同じ目標に向かって取り組めるよう、Mission / Vision / Value の策定を提案し、議論の進行と意見の取りまとめを担いました。
あわせて、何をいつまでに達成するかを示す経営ロードマップの作成も提案し、たたき台を作成しました。

また、リモートワークでは会話が少なく、ちょっとした相談もしにくい状態でした。
そこで、オンラインオフィスとして Gather の導入を提案し、聞きたいことがあればすぐに話しかけられる環境をつくりました。
