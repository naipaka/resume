#### 推し活マッチングアプリ開発

| 項目       | 内容                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| 期間       | 2023/04〜現在                                                            |
| チーム規模 | アプリ開発 3〜4 名、サーバーサイド開発チーム                             |
| 役割       | アプリ設計、API 設計、実装、テスト、チームマネジメント                   |
| 使用技術   | Flutter、Dart、Firebase、StoreKit 2、Pigeon、GitHub Actions、Xcode Cloud |

既存アプリの機能開発と運用を、2023 年から継続して担当しています。
アプリ開発チームは 3〜4 名で、API はサーバーサイドの別チームが実装しています。

仕様とデザインは顧客から提供されるため、どのような API が必要かは、画面を実装するアプリ側で最初に見えてきます。
一方で、API が先に作られると、アプリに必要なデータが含まれず、チーム間のやり取りに手間がかかっていました。
そこで、アプリ側で API 仕様の草案を作ってから実装を始める進め方へ切り替え、最初の草案を作成しました。
その後も、この進め方で開発を続けています。
また、仕様が決まっていない機能や影響の大きい移行では、選択肢を比較して提示し、合意を得てから進めています。
例えば、メンション機能ではデータの持ち方を比較して設計し、アプリ内課金の StoreKit 2 移行ではサーバー側の検証方式を 2 案で提示しました。
StoreKit 2 への移行後も、課金に関する障害や問い合わせは発生していません。

原因がすぐにわからない不具合の調査も、継続して担当しています。
これまでに、クラッシュレポートを影響するユーザーの多いものから整理して修正したり、アプリの容量が膨らみ続ける問題をライブラリの不具合まで遡って解消したりしました。
中でも、プッシュ通知を受け取ったときのアプリ側の処理が特定の条件で実行されない不具合では、エラーが記録されず、チーム内でも再現できないまま調査が止まっていました。
そこで、アプリの状態と起動方法の組み合わせを検証して再現条件を特定し、OS ごとに異なる原因を突き止めて解消しました。

さらに、リリース作業の自動化にも取り組みました。
以前は各開発者が手元の環境でリリースビルドを作っていたため、Xcode のバージョン違いでビルドに失敗したり、リリースする変更が含まれていなかったりする問題がありました。
そこで、GitHub Actions と Xcode Cloud でビルドからストア提出の直前までを自動化し、誰が実行しても同じ環境と手順でリリースできるようにしました。
その結果、人が操作する時間は 1 回のリリースにつき約 1〜2 分になりました。
Xcode Cloud は無料枠で運用しており、構築した仕組みはほかのプロジェクトにも展開しています。

参考：[Xcode Cloud を使った TestFlight デプロイの構築記録](https://zenn.dev/naipaka/scraps/807963171ec6d9)

自社の家庭菜園サポートアプリ「めでた！」を、iOS、Android、macOS 向けに新規開発しました。
要件定義、UI 設計から、Flutter アプリ、Go による API、Cloud Run と Cloud SQL を用いたインフラまでを担い、初期リリースまでは一人で進めました。

アプリ開発者がサーバーまで担う社内初のプロジェクトだったため、アプリ、API、管理用アプリ、API 定義を 1 つのリポジトリにまとめました。
さらに、OpenAPI の定義からアプリとサーバーの両方のコードを生成し、API の変更を 1 つの定義から両方へ反映して、食い違いを型で検出できるようにしました。

また、主要機能のタイムラプス動画は、当初サーバー側で生成していましたが、利用していたライブラリに商用利用上のライセンス懸念が見つかりました。
そこで、機能を維持したままリスクを避けるため、iOS と Android の標準機能でアプリ内に動画を生成する方式へ切り替え、ネイティブ実装を Flutter のプラグインとして切り出しました。

また、ユーザー同士が日記を見せ合うサービスとして公開するには通報の仕組みが欠かせないと判断し、ユーザーや日記への通報を受け付ける API と、運営が通報を審査するための管理用アプリを作成しました。
審査結果に応じたペナルティの付与まで実装しています。

サブスクリプションによるプレミアムプランでは、レシートの検証、ストアからの通知の処理、購入の復元まで、アプリとサーバーの両方を実装しました。
サーバー側でのレシート検証は参考になる実装例がほとんどなかったため、自前のサーバーで 1 つずつ動作を確かめながら作り上げました。
販売する商品は、管理用アプリから変更できるようにしました。

さらに、自分で操作していて日記一覧の画像の読み込みが遅いと感じたため、投稿された画像から幅 400px のサムネイルを生成する仕組みを追加しました。
既存の約 1.4 万枚の画像にも並列処理でサムネイルを生成し、一覧で読み込む画像のサイズを約 98％削減しました。

#### コード品質とレビュープロセスの改善

PR レビューでは、規約の確認や設計のすり合わせがテキスト上に集中し、1 つの PR でコメントのやり取りが数十件に及ぶことがありました。
そこで、機械的に判定できる規約は、社内の lint パッケージに Custom Lint のルールを 9 件追加し、エディタと CI で検出できるようにしました。
導入後、対象にした規約についての指摘はレビューで出ていません。
一方、設計や実装の判断が必要な箇所は、モブプログラミング形式で、その場で一緒に確認しながら修正する方法に切り替えました。
その結果、やり取りは数件まで減り、PR のマージが早まったことで、再レビューで使っていた時間を機能実装へ回せるようになりました。
なお、追加した lint ルールは社内のほかのプロジェクトでも使われ、社外のリポジトリからも利用されています。

中でも、サポートチャット機能はほぼ一人で実装しました。

そこで、1 つの MergeRequest に 3 人のレビュアをランダムに割り当てる制度を提案し、ルールをつくって導入しました。

プロジェクトを離れる際には、後から入るメンバーのために、Flutter の書き方や便利なパッケージ、エディタや Git の使い方をドキュメントにまとめました。
